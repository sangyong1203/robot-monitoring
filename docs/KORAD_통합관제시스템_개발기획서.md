# KORAD 로봇 통합 관제시스템 개발 기획서

## 1. 문서 목적

이 문서는 KORAD 로봇 통합 관제시스템 프론트엔드 개발 착수를 위한 기준 문서이다.
Codex 또는 프론트엔드 개발자가 이 문서를 읽고 Vue 프로젝트 구조 구성, 화면 개발, API 함수 정의, Mock 데이터 연동, 백엔드 전달용 데이터 계약 작성을 시작할 수 있도록 요구사항을 개발 단위로 정리한다.

본 문서는 다음 원칙을 따른다.

- `docs/KORAD 로봇 통합 관제시스템 요구사항 정리본.docx`의 사업 배경, 운영 시나리오, 안전 요구사항을 반영한다.
- `docs/과업지시서_KORAD 로봇통합관제시스템 개발_트리거테크_260807_v08.pdf`의 관리 화면 기능을 개발 범위에 포함한다.
- 백엔드 API와 실제 로봇 연동 방식은 아직 확정되지 않았으므로 프론트엔드 API 함수와 데이터 계약을 추상 인터페이스 기준으로 설계한다.

Codex는 개발 착수 시 이 기획서를 우선 구현 기준으로 사용한다. 원본 DOCX와 PDF는 요구사항 추적이나 원문 확인이 필요한 경우에만 참고하며, 기본 기능 범위를 파악하기 위해 다시 분석할 필요는 없다. 이 기획서와 원본 문서가 충돌하면 임의로 판단하지 않고 사용자에게 확인한다.

## 2. 사업 배경

KORAD 경주 중저준위 방사성폐기물 처분시설에는 방사성폐기물 처리와 시설 감시 업무를 자동화하기 위한 이기종 로봇 6종 7대가 도입된다.

기존에는 작업자가 지게차, 크레인, 순찰 업무를 직접 수행했다. 시스템 도입 후에는 관제실에서 로봇 상태와 임무를 원격으로 모니터링하고, 이상 상황이 발생하면 관제 화면과 로봇 카메라를 통해 1차 확인한 뒤 현장 지원 인력이 2차 조치하는 운영 구조로 전환한다.

주요 목적은 다음과 같다.

- 방사선 구역 내 작업자 체류시간과 피폭 위험을 줄인다.
- 중량물 취급과 반복 운반 작업을 자동화한다.
- 폐기물 처리 과정의 인적 오류를 줄인다.
- 시설 내외부 감시와 순찰을 상시화한다.
- 다기종 로봇의 임무, 상태, 이벤트, 이력을 통합 관리한다.
- 국가 보안시설에 적합한 폐쇄망 기반 무인 감시체계를 구축한다.

## 3. 개발 범위

개발 범위는 Vue 기반 프론트엔드 UI로 한정한다. 관리자 백오피스, 통합 관제, 로봇 제어, 미션 관리, 알림, 통계 및 데이터 관리 화면을 Mock 데이터로 완성하고, 실제 백엔드 API가 제공되면 API 함수 구현과 데이터 매핑만 교체할 수 있는 구조로 개발한다.

프론트엔드 개발 결과에는 다음을 포함한다.

- 전체 메뉴와 화면 UI
- 라우팅과 레이아웃
- 화면 단위 상태와 사용자 상호작용
- 명시적인 요청·응답 타입을 사용하는 API 함수
- API 응답과 화면 모델 사이의 매퍼
- 정상, 빈 결과, 오류, 통신 두절, 비상상황을 포함한 Mock JSON
- 로봇 위치, 배터리, 상태, Mission 진행, 이벤트를 재현하는 Mock 실시간 시뮬레이션
- 백엔드 전달용 OpenAPI 문서, 데이터 스키마, 예시 JSON, 상태값 정의

포함 기능은 다음과 같다.

- 로그인 및 권한 기반 접근 제어
- 기관, 사이트, 지역, 구역, 지도 관리
- 사용자 및 알림 수신자 관리
- 로봇 모델 관리
- 운영 로봇 등록 및 상세 관리
- 로봇 상태 모니터링
- 지도 기반 로봇 위치 관제
- 목적지 관리
- 수동 제어
- 자동 제어 및 스케줄 관리
- Activity, Task, Mission 생성 및 관리
- 2종·2대 이상 로봇의 Mission 및 Task 간 연계 조건 관리
- 운영·이벤트 코드 등록 및 관리
- 관제 화면 팝업 알림
- SMS 알림
- 로봇 운영 이력, 알림/이벤트, 미션 수행 결과, 배터리/상태 이력 중심의 기본 통계
- 데이터 검색 및 다운로드
- 비상정지, Safe Stop, 통신 두절, 장애 대응 UI와 Mock 동작

백엔드 서버, DB, 실제 로봇 제조사 API, 실제 SMS 발송, Private LTE 장비와 서버 배포는 다른 담당자가 구현한다. 프론트엔드는 해당 기능을 호출하기 위한 함수, 요청·응답 타입, 화면 상태, Mock 처리, 데이터 계약까지만 구현한다.

## 4. 운영 대상 로봇

시스템은 총 6종 7대의 로봇을 운영 대상으로 한다.

- 무인지게차 1대: 폐기물 팰릿 상차 및 실내 이송
- 저상형 AMR 2대: 저장소와 처분용기 구간의 팰릿 단위 연속 운반
- 산업용 로봇 1대: 팰릿 위 드럼을 처분용기에 정밀 장입
- 편심 자율주행 로봇 1대: 건물과 시설물 인근 중간 험지 감시
- 4족 보행 로봇 1대: 외곽 경계와 복합 험지 감시
- 실외 자율주행 로봇 1대: 보행로와 일반 차도 감시

시스템은 개별 로봇 제어뿐 아니라 여러 로봇이 하나의 업무 시나리오를 순차 또는 조건 기반으로 수행하는 융합 미션을 지원해야 한다.

## 5. 핵심 업무 시나리오

### 5.1 폐기물 이송 및 장입

폐기물 이송 및 장입 시나리오는 무인지게차, AMR 2대, 산업용 로봇이 협력하는 복합 미션이다.

기본 흐름은 다음과 같다.

1. 무인지게차가 정해진 위치의 폐기물 팰릿을 들어 AMR에 상차한다.
2. AMR 1호기가 팰릿을 처분용기 앞으로 운반한다.
3. 산업용 로봇이 팰릿 위 드럼을 하나씩 처분용기에 장입한다.
4. AMR 2호기는 다음 팰릿을 받은 뒤 대기한다.
5. AMR 1호기가 빈 팰릿을 반출한다.
6. AMR 2호기가 처분용기 앞으로 이동한다.
7. AMR 1호기는 다시 팰릿 적재 위치로 이동한다.
8. 두 AMR이 교대로 운반하고 산업용 로봇이 장입 작업을 반복한다.

개발 시에는 이 흐름을 단순 순차 실행으로 고정하지 않고, Activity, Task, Mission, 조건, 우선순위, 대기 상태, 완료 상태를 조합하는 구조로 구현한다.

### 5.2 외부 안전감시 및 순찰

외부 감시는 편심 자율주행 로봇, 4족 보행 로봇, 실외 자율주행 로봇이 담당 영역을 나누어 동시에 수행한다.

감시 대상은 다음과 같다.

- 외부 침입 흔적
- 시설물 파손 또는 훼손
- 건물 외벽 균열
- 유해가스와 대기오염
- 화재
- 낙상자 또는 쓰러짐
- 시설 주변의 기타 안전 이상

이상 상황이 발생하면 관제 화면 팝업과 SMS 알림이 발생해야 한다. 관제 운용자는 관제 화면과 로봇 탑재 카메라를 통해 상황을 1차 확인하고, 필요 시 현장 지원 인력에게 2차 조치를 요청한다.

### 5.3 표준 운영 절차

시스템은 다음 운영 절차를 지원해야 한다.

1. 관제 운용원이 로그인한다.
2. 전체 로봇의 자가진단 상태와 배터리 잔량을 확인한다.
3. 정상 로봇을 운용 대기 상태로 전환한다.
4. 사전에 설정된 스케줄에 따라 임무를 자동 실행한다.
5. 관제 화면에서 전체 로봇의 운행 상태를 상시 모니터링한다.
6. 경보 발생 시 관제 화면과 로봇 카메라로 1차 원격 확인한다.
7. 필요한 경우 현장 지원 인력이 출동하여 2차 조치한다.
8. 운영 인력 교대 시 운영 이력과 현재 상태를 기반으로 인수인계한다.

## 6. 사용자 및 권한

### 6.1 사용자 등급

시스템은 다음 사용자 등급을 지원한다.

- 수퍼 관리자: 모든 기관과 시스템 설정에 접근할 수 있다.
- 관리자: 소속 기관과 하위 기관의 설정, 사용자, 지도, 미션, 코드, 알림을 관리한다. 로봇 모델과 운영 로봇은 조회만 가능하다.
- 운영자: 관제, 조회, 다운로드, 운영 상태 확인, 허용된 제어 기능을 수행할 수 있다.
- 일반사용자: 로그인 계정이 없는 알림 수신자 또는 로봇 사용자 식별 그룹으로 활용한다.

### 6.2 권한 원칙

권한은 기관 계층과 사용자 등급을 함께 기준으로 판단한다.

- 수퍼 관리자는 전체 기관을 볼 수 있다.
- 관리자와 운영자는 자신이 속한 기관과 허용된 하위 기관만 볼 수 있다.
- 운영 중인 기관 또는 운영 중인 로봇은 삭제를 제한한다.
- 제어 명령, 설정 변경, 삭제와 같은 중요 작업은 사용자 비밀번호 재확인을 요구한다.
- 신규 사용자 ID는 중복을 허용하지 않는다.
- 계정 ID 찾기와 비밀번호 찾기 기능은 제공하지 않는다.
- 비밀번호 변경은 관리자 이상의 사용자만 수행한다.

## 7. 기능 기획

### 7.1 로그인

사용자는 ID와 패스워드로 로그인한다.

신규 등록된 사용자는 최초 로그인 시 패스워드를 설정해야 한다. 로그인 후 사용자 권한에 따라 접근 가능한 메뉴와 기관 범위가 달라진다.

### 7.2 기관 및 사이트 관리

기관 관리는 대표 기관, 소속 기관, 하위 기관의 3단계 구조를 지원한다.

기관 및 사이트 관리 첫 화면에는 등록된 모든 기관을 목록으로 표시한다. 목록에는 다음 정보를 표시한다.

- 기관 명칭
- 기관 관리자 이름과 연락처
- 소속 기관 수와 하위 기관 수
- 운영 중 기관 수
- 운영 중 로봇 수
- 등록 사용자 수
- 최초 등록 일시
- 최근 수정 일시

목록에서 편집과 삭제를 실행할 수 있고, 항목을 더블클릭하면 편집 화면으로 진입한다. 화면 상단에는 신규 등록 기능을 제공한다.

기관 관리 기능은 다음을 포함한다.

- 기관 목록 조회
- 대표 기관 등록
- 소속 기관 등록
- 하위 기관 등록
- 기관 정보 수정
- 기관 비활성화
- 비활성 기관 삭제
- 기관별 운영관리업체 정보 관리
- 기관별 관리자 연결

기관별 관리자는 1명을 기본으로 하며, 대표 기관 관리자는 소속 기관과 하위 기관의 관리자 권한을 함께 가진다.

기관 등록 및 수정 정보는 다음을 포함한다.

- 대표 기관 명칭과 주소
- 소속 기관 명칭과 주소
- 하위 기관 명칭과 주소
- 소속 기관 사용 여부
- 하위 기관 사용 여부
- 운영관리업체의 업체명
- 운영관리업체 담당자의 이름, 소속, 연락처
- 등록 사용자 정보
- 운영 상태 또는 비활성 상태

대표 기관으로 등록할 때 소속 기관 또는 하위 기관 사용 여부를 선택할 수 있어야 한다. 사용을 선택한 경우 최소 1개 이상의 소속 기관 또는 하위 기관을 등록해야 한다.

협력사 또는 고객사는 필요한 경우 최하위 기관에 지정할 수 있다.

기관 정보 수정 후 저장할 때 적용 또는 취소를 선택하는 최종 확인 팝업을 표시한다. 운영 중인 기관은 바로 삭제할 수 없으며, 비활성화 후 삭제하도록 안내한다.

### 7.3 사용자 관리

사용자 관리는 기관 선택 후 해당 기관 범위의 사용자를 조회하는 방식으로 구성한다.

첫 진입 시에는 사용자 목록을 표시하지 않는다. 대표 기관, 소속 기관, 하위 기관을 복수로 선택하고 조회한 뒤 결과를 표시한다. 수퍼 관리자는 전체 기관을 선택할 수 있고, 관리자와 운영자는 자신의 소속 범위와 허용된 하위 기관만 선택할 수 있다.

사용자 목록에는 다음 정보를 표시한다.

- 소속 기관 경로
- 사용자 등급
- ID
- 이름
- 휴대전화 번호
- 이메일 주소
- 사용 또는 미사용 상태
- 최초 등록 일시
- 최근 수정 일시

목록에서 편집과 삭제를 실행할 수 있고, 항목을 더블클릭하면 편집 화면으로 진입한다. 화면 상단에는 신규 사용자 등록 기능을 제공한다.

기능은 다음을 포함한다.

- 기관 기준 사용자 목록 조회
- 신규 사용자 등록
- 사용자 정보 수정
- 사용자 삭제
- 사용자 사용 상태 변경
- 일반사용자 지정 양식 파일 일괄 등록
- 비밀번호 변경
- 알림 수신 여부 설정
- 알림 수신 방법 설정

사용자 등록 및 수정 정보는 다음을 포함한다.

- 사용자 등급
- 소속 기관
- ID
- 이름
- 휴대전화 번호
- 이메일 주소
- 긴급상황 알림 수신 여부
- 서비스 알림 수신 여부
- 알림 수신 방법
- 계정 생성 일시
- 마지막 로그인 일시
- 메모

신규 사용자 ID는 중복 확인을 거치며, 10자 이하의 영문과 숫자 조합으로 등록한다. 신규 사용자는 최초 로그인 시 비밀번호 설정 팝업을 통해 비밀번호를 설정한다. PDF에 기재된 비밀번호 조합 문구는 최소 길이와 필수 조합이 명확하지 않으므로 정책값으로 분리하고 확정 후 적용한다.

계정 ID 찾기와 비밀번호 찾기 기능은 제공하지 않는다. 편집 화면의 비밀번호 변경 기능은 관리자 이상에게만 제공한다.

사용자별 알림 수신 방법은 SMS로 설정한다. 관제 화면 팝업은 개인 수신 채널이 아니라 알림 규칙과 화면 접근 권한에 따라 관제 화면에 표시한다.

### 7.4 지역, 구역, 지도 관리

시스템은 다지역, 다구역, 다지도 구조를 지원해야 한다.

공간 계층은 다음 개념으로 관리한다.

- 지역: KORAD 전체 시설 단위 또는 대규모 운영 단위
- 구역: 지역 안의 주요 운영 구역
- 지도: 구역에 속한 실내 또는 실외 지도
- 목적지: 지도 위에서 로봇이 이동하거나 작업할 수 있는 좌표 또는 방향 정보

지역과 구역 관리는 수퍼 관리자만 접근하고 수정할 수 있다. 지역/구역 목록 화면 상단에는 신규 지역 등록과 신규 구역 등록 기능을 제공한다. 지역은 등록된 구역을 선택하여 구성하고, 구역은 등록된 지도를 선택하여 구성한다.

시스템은 지역에 여러 구역, 구역에 여러 지도를 등록할 수 있는 구조로 개발한다. 대표 구역은 반드시 하나를 지정하며, 대표 구역에 포함된 운영 로봇의 좌표를 관제 지도 좌표계에 논리적으로 동기화한다. KORAD 초기 구성은 1개 지역, 운영 지도 2개를 기준으로 시작하되 추가 지역과 구역을 제한하지 않는다.

지도 관리 진입 화면에는 접근 가능한 등록 지도 목록을 표시한다. 수퍼 관리자는 전체 기관의 지도를 조회하고, 기관별 사용자는 소속 기관의 지도만 조회한다.

지도 목록에는 다음 정보를 표시한다.

- 자동 생성된 지도 식별 ID
- 등록 기관
- 등록 사용자
- 지도 이름
- 파일 이름과 크기
- 연계 로봇 모델
- 지도 설명
- 사용 또는 미사용 상태
- 축척
- 최초 등록 일시
- 최근 변경 일시
- 2D 썸네일

각 지도 항목에서 다운로드, 목적지 보기, 지도 파일 교체, 삭제를 실행할 수 있고, 화면 상단에는 지도 등록 기능을 제공한다.

기능은 다음을 포함한다.

- 지역 등록 및 수정
- 구역 등록 및 수정
- 지도 등록 및 수정
- 대표 구역 설정
- 대표 지도 설정
- 지도 파일 업로드
- 2D 지도 썸네일 또는 미리보기
- 지도 다운로드
- 지도 교체
- 지도 삭제
- 지도 사용 여부 설정
- 목적지 관리 화면 진입

지도 등록 정보는 지도 이름, 지도 파일, 지도 설명, 사용 여부를 포함한다. 식별 ID, 등록자, 파일 정보, 등록·변경 일시는 시스템이 자동으로 관리한다. 목적지는 지도 등록이 완료된 후 해당 지도의 목적지 관리 화면에서 등록한다.

대표 구역과 대표 지도는 통합 관제 모니터링 화면에서 기본 지도로 사용된다.

대표 지도가 하나뿐인 경우에는 삭제할 수 없다. 다른 지도를 대표 지도로 선택하면 최종 확인 후 기존 대표 지도를 미사용 상태로 변경한다.

각 로봇의 실제 좌표는 운영 지도 좌표계에 논리적으로 매핑되어야 한다. 좌표계 변환 방식은 외부 로봇 및 지도 포맷이 확정된 뒤 인터페이스 명세에서 상세화한다.

### 7.5 목적지 관리

목적지는 특정 지도에 종속된다.

목적지 관리 화면은 지도 목록의 목적지 보기 기능을 통해 진입한다. 화면 제목에는 등록 기관명, 지도 이름, 목적지 관리를 표시한다.

목적지 목록에는 다음 정보를 표시한다.

- 목적지 타입
- 목적지 이름
- 2D 위치 좌표
- 방향 좌표

각 목적지 항목에는 지도에서 위치를 확인하는 기능과 수정 기능을 제공한다. 위치 확인 화면은 왼쪽의 확대·축소·이동 가능한 지도와 오른쪽의 목적지 목록 및 이름 검색 영역으로 구성한다.

기능은 다음을 포함한다.

- 목적지 목록 조회
- 신규 목적지 등록
- 목적지 수정
- 목적지 일괄 등록
- 목적지 등록 양식 다운로드
- 지도 위 목적지 위치 확인
- 목적지 이름 검색
- 지도 확대, 축소, 이동

일괄 등록은 지정 양식 파일만 허용하고, 양식이 맞지 않으면 오류 내용을 팝업으로 안내한다.

목적지는 로봇 수동 제어, 자동 제어, Activity, Task, Mission에서 참조된다.

### 7.6 로봇 모델 관리

로봇 모델은 실제 운영 로봇의 원형 정보이다.

로봇 모델 관리 메뉴는 관리자 이상에게 표시한다. 관리자는 소속 기관의 모델을 조회할 수 있고, 신규 등록과 수정은 수퍼 관리자만 수행한다.

화면 상단에는 기관 선택과 검색 영역을 제공하고, 하단에는 로봇 모델 목록을 표시한다. 수퍼 관리자는 전체 기관을 선택할 수 있다.

로봇 모델 목록에는 다음 정보를 표시한다.

- 소속 기관 경로
- 로봇 모델명
- 제조사
- OS
- 등록된 운영 로봇 수
- 최초 등록 일시
- 최근 수정 일시

각 항목에서 상세 확인과 수정을 실행할 수 있고, 화면 상단에는 신규 모델 등록 기능을 제공한다.

기능은 다음을 포함한다.

- 로봇 모델 목록 조회
- 신규 로봇 모델 등록
- 로봇 모델 상세 확인
- 로봇 모델 수정
- 로봇 모델 사용 여부 관리
- 로봇 모델 이미지 등록
- 제조사, OS, 분류 정보 관리
- 로봇 설정 키 관리
- 로봇 모니터링 항목 활성화 또는 비활성화

신규 모델 등록 정보는 기관, 로봇 모델명, 제조사, OS, 모델 이미지, 로봇 설정, 모니터링 항목을 포함한다. 모델 이미지는 600x800 픽셀, 5MB 이하 파일을 기준으로 검증한다. 로봇 설정은 키, 설정값, 설명으로 구성하고 별도 편집 화면에서 추가·수정한다.

모니터링 항목은 로봇 모델별로 달라질 수 있다. 예시는 다음과 같다.

- 목적지 기반 제어 지원 여부
- 수동 주행 제어 지원 여부
- 카메라 #1~#3 채널별 실시간 영상 지원 여부
- 로봇 메인 디스플레이 화면 공유 지원 여부
- Lidar, 온도, 습도, 기압, 적외선, 초음파, 압력, 하중 등 센서 그룹

실제 센서 항목은 로봇 제조사 연동 사양 확정 후 정리한다.

### 7.7 운영 로봇 관리

운영 로봇은 로봇 모델에서 파생되어 실제 기관 또는 사이트에 설치된 로봇이다.

운영 로봇 관리 메뉴는 운영자 이상에게 표시한다. 운영자와 관리자는 허용된 기관 범위의 정보를 조회하고, 신규 등록과 편집은 수퍼 관리자만 수행한다.

화면 상단에는 기관, 로봇 모델, 검색 조건을 제공하고, 하단에는 운영 로봇 목록을 표시한다. 수퍼 관리자는 기관과 로봇 모델에서 전체를 선택할 수 있고, 관리자와 운영자는 소속 기관 범위만 선택할 수 있다.

운영 로봇 목록에는 다음 정보를 표시한다.

- 운영 또는 미운영 상태
- 분류
- 자동 생성된 로봇 ID
- 로봇 이름
- 메모
- 로봇 모델명
- 제조사
- 소속 기관 경로

목록의 확인 기능 또는 항목 더블클릭으로 상세 화면에 진입하고, 화면 상단에는 신규 운영 로봇 등록 기능을 제공한다.

기능은 다음을 포함한다.

- 운영 로봇 목록 조회
- 신규 운영 로봇 등록
- 운영 로봇 상세 조회
- 운영 로봇 정보 수정
- 운영 로봇 삭제
- 운영 상태 표시
- 운영 로봇 모니터링 화면 진입
- 로봇 모델과 기관 연결

신규 운영 로봇 등록 정보는 기관, 로봇 모델, 자동 표시되는 제조사, 로봇 이름, 메모를 포함한다.

운영 로봇 상세 화면은 다음 정보를 표시한다.

- 등록 기관
- 로봇 이름
- 로봇 모델
- 제조사
- 운영 상태
- 메모
- 활성화된 모니터링 항목
- 최근 상태 수신 시각
- 배터리 상태
- 현재 위치
- 통신 상태

상세 화면 상단에는 등록 기관명, 로봇 이름, 로봇 모델명, 운영 상태를 표시한다. 운영 중일 때만 운영 로봇 모니터링 기능을 활성화한다. 수정, 삭제, 목록 이동 기능을 제공하며, 삭제는 경고 팝업과 사용자 비밀번호 확인을 거친다.

### 7.8 통합 관제 화면

통합 관제 화면은 운영자가 가장 자주 사용하는 화면이다.

주요 기능은 다음과 같다.

- 대표 지도 또는 선택 지도 표시
- 지도 위 로봇 현재 위치 표시
- 로봇 상태 목록 표시
- 로봇별 배터리, 통신, 운행 상태 표시
- 진행 중인 미션 표시
- 알림 및 이벤트 표시
- 로봇 선택 시 상세 상태 표시
- 카메라 영상 영역 표시
- 긴급 정지 또는 Safe Stop 명령 진입
- 운영 이력 진입

관제 화면은 높은 가독성과 빠른 판단을 우선한다. 장식적인 화면보다 운영자가 상태, 위치, 경보, 제어 가능 여부를 빠르게 파악할 수 있는 구조로 설계한다.

### 7.9 로봇 제어

로봇 제어는 수동 제어와 자동 제어를 지원한다.

운영자 이상이 접근하고 설정할 수 있다. 화면 상단에는 기관의 운영 중 로봇 목록을 표시하고, 하단에는 선택한 로봇의 운영 상황을 표시한다. 운영 상황에는 로봇 이름, 현재 좌표, 수동 제어 실행 중·스케줄 실행 중·대기 중·충전 중·전원 꺼짐 등의 상태를 표시한다. 운영 상황 영역에는 수동 제어와 신규 자동 제어 등록 기능을 제공한다.

수동 제어는 운영자가 특정 로봇을 선택하고 목적지, Activity, Task, Mission 중 허용된 단위를 선택하여 즉시 실행 명령을 내리는 방식이다.

자동 제어는 Task 또는 Mission에 월별·주간·일별 시간 주기, 영구 반복·횟수 반복 조건, 등록된 운영·이벤트 코드 조건을 연결하여 스케줄로 실행하는 방식이다.

제어 기능의 공통 원칙은 다음과 같다.

- 운영 중인 로봇만 제어 대상으로 선택할 수 있다.
- 로봇 상태가 대기 중이 아닌 경우 자동 제어 실행을 제한할 수 있다.
- 다중 로봇 제어는 모든 실행 조건이 충족되어야 시작한다.
- 모든 제어 명령과 설정 변경은 사용자 비밀번호 재확인을 거친다.
- 제어 명령의 요청, 전송, 응답, 실패, 취소, 완료 이력을 기록한다.

### 7.10 Activity, Task, Mission 관리

시스템은 로봇 임무를 다음 계층으로 관리한다.

- Activity: 로봇이 수행하는 최소 실행 단위
- Task: 2개 이상의 Activity를 조합한 단일 로봇 작업 단위
- Mission: 하나 이상의 Task를 조합한 단일 또는 다중 로봇 시나리오
- Schedule: Mission 또는 Task를 시간 조건과 반복 조건에 따라 실행하는 계획

단일 로봇의 임무는 Task 단위로 생성하고 관리한다. 2종·2대 이상의 로봇이 함께 수행하는 임무는 Mission 단위로 생성하고 관리하며, 로봇별 Task 사이의 선행·완료·상태 조건을 연결하여 연속된 흐름을 구성한다. PDF에서 말하는 "융합 시나리오"는 별도 기능이 아니라 이 다중 로봇 Mission을 의미한다.

예를 들어 특정 AMR이 대기 위치에 있고, 다른 로봇의 특정 Activity가 완료되었을 때 다음 이동을 시작하는 방식의 조건을 구성할 수 있어야 한다.

Mission 관리 기능은 다음을 포함한다.

- Activity 생성, 수정, 사용 여부 관리
- Task 생성, 수정, 사용 여부 관리
- Mission 생성, 수정, 사용 여부 관리
- Schedule 생성, 수정, 사용 여부 관리
- 로봇별 Activity 조합
- Task 간 선행 조건 설정
- Mission 실행 조건 설정
- 반복 실행 조건 설정
- 실행 중이거나 참조 중인 Activity, Task, Mission 삭제 제한
- Mission 실행 결과 기록

### 7.11 코드 관리

이 절의 "코드"는 프로그램 소스코드가 아니다. 운영 로봇의 Mission, Activity, Task, Schedule, 목적지, 감시·순찰 이벤트, 센서·모니터링 값과 관련된 상황을 식별하고 처리하기 위한 업무 코드이다. 코드 관리 화면에서 등록한 코드는 자동 제어 실행 조건, 즉시 조치, 후속 조치, 알림, 이력 분류에 사용한다.

코드 관리는 관리자 이상에게만 표시한다. 수퍼 관리자는 모든 기관의 코드를 조회하고, 관리자는 소속 기관의 코드만 조회한다. 화면 상단에는 기관 선택, 코드 분류 선택, 검색 기능을 제공하고, 하단에는 코드 목록을 표시한다.

코드 목록에는 다음 정보를 표시한다.

- 기관
- 코드 분류
- 처리 결과 유형
- 상황 또는 상태 등급
- 대상 로봇 수
- 등록자
- 등록 일시
- 최근 수정 일시

코드 분류는 센서 및 각종 모니터링 값 등 운영 데이터를 구분한다. 처리 결과 유형은 Activity, Task, Logic 등과 연결할 수 있다. 상황 또는 상태 등급은 PDF 예시가 불명확하므로 최종 명칭과 단계값을 확정 가능한 설정값으로 관리한다.

목록 항목을 더블클릭하면 코드 상세 확인 또는 편집 화면으로 진입한다. 각 항목에 편집과 삭제 기능을 제공하고, 화면 상단에는 신규 코드 등록 기능을 제공한다.

코드 관리 기능은 다음을 포함한다.

- 코드 분류 관리
- 코드 목록 조회
- 신규 코드 등록
- 코드 수정
- 코드 삭제
- 상황 조건 설정
- 코드 결과 설정
- 대상 로봇 범위 설정
- 코드 기반 알림 연결
- 코드 기반 자동 제어 조건 연결

코드는 개별 로봇 상황과 2종 이상의 로봇이 수행하는 Mission 상황을 모두 표현할 수 있어야 한다. 여러 코드 조건을 조합한 자동 제어는 등록된 모든 조건이 충족되어야 실행하는 것으로 표시한다.

### 7.12 알림 관리

MVP 알림 채널은 관제 화면 팝업과 SMS로 정의한다.

화면 상단에는 기관 선택, 알림 분류 선택, 검색 기능을 제공하고, 하단에는 알림 목록을 표시한다. 수퍼 관리자는 전체 기관을 선택할 수 있고, 관리자와 운영자는 허용된 기관 범위만 선택할 수 있다.

알림 목록에는 다음 정보를 표시한다.

- 기관
- 연결된 운영·이벤트 코드
- 알림 유형
- 대상 로봇 수
- 등록자
- 등록 일시
- 최근 수정 일시

알림 유형은 관제 화면 팝업과 SMS로 제공한다. 목록 항목을 더블클릭하면 상세 확인 또는 편집 화면으로 진입하고, 각 항목에 편집과 삭제 기능을 제공한다.

알림 관리 기능은 다음을 포함한다.

- 알림 목록 조회
- 신규 알림 등록
- 알림 수정
- 알림 삭제
- 알림 분류 설정
- 운영·이벤트 코드와 알림 연결
- 대상 로봇 설정
- 대상 사용자 또는 일반사용자 그룹 설정
- 관제 화면 팝업 발생
- SMS 발송 요청
- 알림 이력 기록

알림은 운영자 이상 사용자가 설정할 수 있다. SMS는 발송 요청 API 함수와 요청·성공·실패 Mock 응답을 구현하며, 실제 발송은 백엔드 API 연동 시 데이터 매핑으로 교체한다.

### 7.13 통계 및 데이터 관리

통계와 데이터 관리는 운영자 이상 사용자가 접근할 수 있다.

기본 통계 범위는 다음과 같다.

- 로봇 운영 이력
- 알림 및 이벤트 이력
- 미션 수행 결과
- 배터리 상태 이력
- 로봇 상태 이력

기본 통계 화면은 다음 지표를 우선 표시한다.

- 로봇별 운행시간과 운행횟수
- 알림·이벤트 발생 건수와 처리 상태별 건수
- Mission 성공·실패·취소 건수와 평균 수행시간
- 로봇별 평균·최저 배터리 잔량
- 로봇 상태별 누적 지속시간

기능은 다음을 포함한다.

- 기관 기준 필터
- 로봇 기준 필터
- 기간 기준 필터
- 이벤트 유형 기준 필터
- 미션 기준 필터
- 검색 조건별 결과 수치 표시
- 결과 다운로드
- 기본 통계 그래프 표시
- 선택 통계의 대시보드 반영

검색 결과는 대량 데이터일 수 있으므로 화면 목록 표시보다 조건 요약, 결과 수치, 다운로드 중심으로 설계한다.

사용 흐름은 조건 선택, 검색 실행, 적용 조건과 결과 건수 확인, 결과 다운로드 순서로 통일한다. 화면 최상단에는 기본 통계 그래프를 상시 표시하고, 사용자가 선택한 그래프를 대시보드에 반영한다. 기본 그래프의 개수와 세부 시각화 방식은 통계 화면 설계 시 확정한다.

### 7.14 비상 대응

시스템은 다음 비상상황을 고려한다.

- 통신 두절
- 로봇 고장
- 정전
- 시스템 장애
- 위험 이벤트 발생
- 현장 안전 이상 발생

필수 기능은 다음과 같다.

- 로봇별 물리적 E-Stop 장착 전제
- 시스템에서 원격 비상정지 명령 제공
- 전체 로봇 Safe Stop 일괄 전송
- 관제 화면 팝업 경보
- 관제실 경보음 또는 시각 경보 연계 가능 구조
- KORAD 안전 담당자 SMS 통보
- 로봇 카메라를 통한 1차 원격 확인
- 현장 지원 인력의 2차 조치 기록
- 관제시스템 장애 시 기존 수작업 체계로 전환하는 Fallback 절차 안내

## 8. 프론트엔드 구조 기획

### 8.1 개발 방식

프론트엔드는 계약 우선 방식으로 개발한다. 화면 컴포넌트는 JSON 파일이나 HTTP 클라이언트를 직접 사용하지 않고, 메뉴별 API 함수만 호출한다.

API 함수는 동일한 요청·응답 타입을 유지하면서 다음 두 모드를 지원한다.

- Mock 모드: Mock JSON과 프론트엔드 메모리 상태를 사용한다.
- Server 모드: 실제 백엔드 API를 호출하고 응답을 화면 모델로 변환한다.

개발 중에는 `VITE_API_MODE=mock`을 기본값으로 사용한다. 백엔드 연동 시에는 `VITE_API_MODE=server`로 전환하며, 화면 컴포넌트가 아니라 API 함수와 매퍼만 수정한다.

### 8.2 Vue 권장 구조

KORAD는 관리자·관제·로봇·미션 등 메뉴 중심 시스템이므로 `Menu-based Architecture`를 사용한다. 프로젝트에 기존 구조가 있으면 기존 구조를 우선하고, 신규 프로젝트라면 다음 구성을 기준으로 시작한다.

```text
code/frontend/
  src/
    pages/
      auth/
        login/
      main/
        dashboard/
        monitoring/
        robotControl/
      admin/
        organizations/
        users/
        regions/
        maps/
        destinations/
        robotModels/
        operatingRobots/
        missions/
        codes/
        alerts/
        statistics/
    components/
    composables/
    http/
    services/
    types/
    constants/
    mappers/
    stores/
    router/
    layouts/
    assets/
  contracts/
    openapi.yaml
    schemas/
    examples/
    enums.md
    backend-handoff.md
```

각 메뉴 폴더는 필요한 경우에만 다음 역할 폴더와 파일을 추가한다.

```text
{menu}/
  {Menu}Page.vue
  components/
  composables/
  service/
    {menu}.api.ts
    {menu}.types.ts
    {menu}.mapper.ts
    {menu}.mock.ts
    {menu}.mock.json
```

구조 적용 원칙은 다음과 같다.

- 특정 메뉴에서만 사용하는 컴포넌트, API, 타입, 매퍼, Mock은 해당 메뉴 안에 둔다.
- 여러 메뉴에서 사용하는 UI만 `src/components/`로 이동한다.
- 여러 메뉴에서 사용하는 Vue 로직만 `src/composables/`로 이동한다.
- 공통 HTTP 클라이언트, 인터셉터, 공통 오류 처리는 `src/http/`에 둔다.
- API 모드 전환과 여러 메뉴에서 사용하는 실시간 Mock은 `src/services/`에 둔다.
- 공통 타입과 매퍼는 실제로 여러 메뉴에서 재사용될 때만 `src/types/`와 `src/mappers/`로 이동한다.
- `src/features/`는 초기에는 만들지 않는다. 여러 메뉴에서 공유되는 대규모 업무 기능이 확인될 때만 추가한다.
- 권장 폴더를 모두 미리 만들지 않고 실제 개발 메뉴에 필요한 폴더만 생성한다.

### 8.3 API 함수와 타입

각 `*.api.ts` 파일은 화면에서 호출하는 API 함수와 명시적인 요청·응답 타입을 사용한다. API 함수는 Vue 상태, 로딩 메시지, 팝업, 테이블 행을 직접 관리하지 않는다.

필요한 프론트엔드 API 함수 범주는 다음과 같다.

- 기관, 사용자, 지역, 구역, 지도, 목적지 조회·등록·수정·삭제
- 로봇 모델 조회·등록·수정
- 운영 로봇 조회·등록·수정·삭제
- 로봇 현재 상태, 위치, 배터리, 통신, 자가진단, 센서, 카메라 정보 조회
- 정상 로봇의 운용 대기 상태 전환 요청
- 수동 제어, 목적지 이동, Activity, Task, Mission 실행 요청
- 정지, 비상정지, Safe Stop, 명령 취소 요청
- Mission, Schedule, 코드, 알림 조회·등록·수정·삭제
- SMS 발송 요청과 발송 결과 조회
- 운영 이력, 알림·이벤트, Mission 결과, 배터리·상태 통계 조회와 다운로드 요청

서버 응답과 화면 표시 형태가 다른 경우 `*.mapper.ts`에서 변환한다. 단순히 같은 필드를 그대로 전달하는 경우에는 불필요한 매퍼를 만들지 않는다.

### 8.4 Mock 데이터

Mock JSON은 백엔드 응답 형식을 기준으로 작성하고, `*.types.ts`의 응답 타입과 일치시킨다. 컴포넌트에서 Mock JSON을 직접 import하지 않고 `*.mock.ts`를 통해 반환한다.

각 주요 화면은 다음 Mock 상황을 제공한다.

- 정상 데이터
- 빈 결과
- 로딩 지연
- 요청 실패
- 권한 없음
- 로봇 통신 두절
- 비상 또는 위험 이벤트
- Mission 진행, 완료, 실패, 취소
- SMS 발송 요청 성공과 실패

정적 JSON은 초기 상태로 사용하고, 등록·수정·삭제·제어 요청은 프론트엔드 메모리 상태를 변경하여 화면에 반영한다. 새로고침 시 초기 상태로 돌아가도 되며, 영구 저장은 프론트엔드 개발 범위에 포함하지 않는다.

### 8.5 실시간 Mock 시뮬레이션

관제 화면 검증을 위해 공통 실시간 Mock 서비스를 제공한다.

시뮬레이션 대상은 다음과 같다.

- 지도 위 로봇 위치 이동
- 운행, 대기, 충전, 전원 꺼짐, 오류 상태 전환
- 배터리 잔량 변화
- 통신 연결, 지연, 두절, 재연결
- Mission 단계와 진행률 변화
- 센서 이상, 침입, 화재, 낙상 등 이벤트 발생
- 관제 팝업과 SMS 요청 상태 변화
- 정지, 비상정지, Safe Stop 요청과 Mock 응답

실시간 Mock은 개발 환경에서 시나리오를 선택해 재현할 수 있어야 한다. 추후 백엔드의 WebSocket 또는 다른 실시간 채널이 확정되면 동일한 화면 이벤트 형태로 매핑한다.

### 8.6 백엔드 전달용 계약

`contracts/`는 Vue 실행 코드가 아니라 프론트엔드와 백엔드가 공유하는 API 계약이다.

다음 내용을 관리한다.

- `openapi.yaml`: API 경로, 요청 방식, 요청값, 응답값, 오류 응답
- `schemas/`: 공통 객체와 실시간 이벤트 데이터 스키마
- `examples/`: API별 요청·응답 예시 JSON
- `enums.md`: 사용자 권한, 로봇 상태, Mission 상태, 이벤트 등급 등 상태값 정의
- `backend-handoff.md`: 화면별 API 사용처, 호출 순서, 미확정 사항, 연동 점검 방법

계약에는 필수값, 선택값, `null` 허용 여부, 날짜·시간대, 좌표와 센서 단위, 페이지 처리, 검색 조건, 오류 코드, 상태 전이를 명시한다. 백엔드는 이 계약과 예시 JSON을 기준으로 API를 구현할 수 있어야 한다.

### 8.7 프론트엔드 책임 범위

프론트엔드에서 비밀번호 재확인, 권한별 메뉴 노출, 파일 형식과 크기 검증, 위험 명령 확인 팝업을 구현한다. 실제 인증·인가, 감사 이력 저장, 로봇 제어 실행, SMS 발송, 보안 장비와 네트워크 제어는 백엔드 또는 인프라 책임이다.

프론트엔드 권한 제어는 사용자 경험을 위한 것이며 보안 경계가 아니다. 백엔드 연동 후 모든 요청은 서버 권한 검사를 통과해야 한다.

## 9. 프론트엔드 개념 데이터 모델

이 장은 DB 구조가 아니라 TypeScript 요청·응답 타입과 화면 모델을 구성하기 위한 개념 관계이다.

핵심 개념은 다음과 같다.

- 기관: 대표 기관, 소속 기관, 하위 기관을 포함하는 조직 단위
- 사용자: 로그인 사용자와 권한 정보를 가진 계정
- 일반사용자: 알림 수신 또는 로봇 사용자 식별을 위한 비로그인 대상
- 지역: 여러 구역을 묶는 공간 단위
- 구역: 여러 지도를 묶는 운영 공간 단위
- 지도: 로봇 위치와 목적지를 표시하는 2D 공간 정보
- 목적지: 지도에 종속된 이동 또는 작업 좌표
- 로봇 모델: 제조사, OS, 설정, 모니터링 항목을 정의하는 원형
- 운영 로봇: 실제 현장에 배치된 로봇의 화면 표시 단위
- Activity: 로봇의 최소 수행 단위
- Task: Activity 조합으로 구성된 작업 단위
- Mission: 단일 또는 다중 로봇 Task를 조건으로 연결한 시나리오
- Schedule: Task 또는 Mission의 시간 기반 실행 계획
- Code: 임무, 목적지, 센서, 모니터링, 이벤트 상황을 식별하는 업무 코드
- Alert: 코드 또는 이벤트에 연결된 관제 팝업 및 SMS 설정
- Event: 로봇, Mission, 시스템에서 발생한 상태 변화 또는 이상 상황
- Command: 프론트엔드가 요청한 로봇 제어 명령과 응답 상태
- History: 운영, 상태, 배터리, Mission, 알림, 제어에 대한 조회 데이터

API 요청·응답 타입과 화면 폼·목록·카드 타입은 형태가 다를 때 분리하고 매퍼로 연결한다.

## 10. 화면 구성

초기 화면 구성은 다음 메뉴 체계를 기준으로 한다.

- 로그인
- 대시보드
- 통합 관제
- 기관 관리
- 사용자 관리
- 지역/구역 관리
- 지도 관리
- 목적지 관리
- 로봇 모델 관리
- 운영 로봇 관리
- 로봇 제어
- 미션 관리
- 코드 관리
- 알림 관리
- 통계 및 데이터 관리
- 운영 이력
- 시스템 설정

화면 개발 시 공통 원칙은 다음과 같다.

- 목록, 상세, 등록, 수정 흐름을 일관되게 유지한다.
- 모든 화면에 로딩, 빈 결과, 오류, 권한 없음 상태를 구현한다.
- 삭제, 제어, 설정 변경 같은 위험 작업은 확인 절차를 둔다.
- 관제 화면은 실시간 상태 인지와 조치 가능 여부를 우선한다.
- 관리자 화면은 검색, 필터, 상태 구분, 다운로드 흐름을 명확히 한다.
- 지도 화면은 확대, 축소, 이동, 목적지 표시, 로봇 위치 표시를 지원한다.
- API 전환 여부가 화면 컴포넌트에 영향을 주지 않도록 한다.

## 12. 우선 구현 기준

1. 기존 프로젝트 구조가 있으면 먼저 확인하고 메뉴 기반 구조에 맞춰 확장한다.
2. 인증, 권한, 기관, 사용자 타입과 Mock API를 먼저 만든다.
3. 각 메뉴는 API 함수와 응답 타입을 먼저 정의한 후 화면을 구현한다.
4. 화면에서 JSON을 직접 사용하지 않고 반드시 API 함수로 접근한다.
5. 지도, 목적지, 로봇 모델, 운영 로봇 등록 흐름을 완성한다.
6. 통합 관제 화면에서 Mock 로봇 위치와 상태를 표시한다.
7. 제어와 Mission은 실제 실행 없이 요청·진행·성공·실패 상태를 시뮬레이션한다.
8. 알림은 관제 팝업과 SMS 발송 요청 Mock을 구현한다.
9. 각 화면 완료 시 OpenAPI와 예시 JSON을 함께 갱신한다.
10. 실제 API가 제공되면 메뉴별 API 함수와 매퍼를 교체하고 화면 회귀를 확인한다.

## 13. 백엔드 계약 미확정 항목

프론트엔드 개발은 Mock 계약으로 진행할 수 있지만, 실제 연동 전 다음 항목을 백엔드 담당자와 확정해야 한다.

- API 경로와 HTTP 방식
- 공통 응답과 오류 응답 형식
- 인증 토큰과 권한 오류 처리 방식
- 목록 검색, 정렬, 페이지 처리 방식
- 로봇 상태와 명령 응답 데이터 형식
- 실시간 연결 방식과 이벤트 메시지 형식
- 카메라 스트림 전달 방식
- 지도 파일 형식과 좌표계
- 센서 항목, 값 타입, 단위
- SMS 발송 요청과 결과 형식
- 데이터 보관 기간과 다운로드 파일 형식
- 날짜·시간대와 `null` 처리 기준
- Mission 및 명령 상태 전이

이 항목은 `contracts/backend-handoff.md`에 기록하고, 확정된 내용은 `openapi.yaml`, 스키마, TypeScript 타입에 함께 반영한다.

## 14. 프론트엔드 개발 주의사항

- 프로젝트의 `README.md`, `AGENTS.md`, 기존 소스 구조를 먼저 확인한다.
- Vue 프로젝트 구조는 로컬 `vue.md`의 Menu-based Architecture를 따른다.
- 메뉴 전용 코드는 해당 메뉴 안에 두고, 재사용이 확인된 코드만 공통 폴더로 이동한다.
- 화면 컴포넌트는 Mock JSON이나 HTTP 클라이언트를 직접 호출하지 않는다.
- API 함수는 명시적인 요청·응답 타입을 사용한다.
- 서버 DTO와 화면 모델이 다를 때만 매퍼를 사용한다.
- Mock과 실제 API는 동일한 함수 시그니처와 응답 타입을 유지한다.
- 로딩, 빈 결과, 오류, 권한 없음, 통신 두절 상태를 빠뜨리지 않는다.
- 제어 명령과 SMS는 실제 동작으로 오해되지 않도록 Mock 상태를 명확히 구분한다.
- 위험 명령은 비밀번호 재확인과 확인 팝업 UI를 거친다.
- 운영 중인 기관, 지도, 로봇, Mission의 삭제 제한 UI를 구현한다.
- 다지역, 다구역, 다지도 확장을 전제로 화면과 타입을 구성한다.
- 새 라이브러리나 구조 변경이 필요하면 사용자 확인 후 적용한다.

## 15. 착수 결론

본 개발은 KORAD 통합 관제시스템의 Vue 프론트엔드 UI와 백엔드 연동 계약을 완성하는 작업이다.

모든 화면은 Mock API와 실시간 Mock 데이터로 독립 실행되어야 한다. 동시에 API 함수, TypeScript 타입, OpenAPI, 예시 JSON을 함께 관리하여 백엔드가 동일한 계약으로 바로 구현할 수 있게 한다. 실제 API가 제공되면 컴포넌트를 수정하지 않고 메뉴별 API 함수와 매퍼를 교체하는 것을 최종 구조 기준으로 한다.
